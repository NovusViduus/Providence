## 1. Project Charter

### 1.1 Problem Statement

Network security monitoring tools are either enterprise-grade and inaccessible to
individuals and small organizations, or they're simple packet sniffers with no
intelligence layer. Meanwhile, the threat landscape is evolving — adversarial AI
agents are increasingly being used to automate attacks, and traditional
signature-based detection systems are not equipped to identify AI-driven attack
patterns.

### 1.2 Product Vision

Providence is a multi-component network security intelligence platform that
provides real-time intrusion detection, attack classification, automated response,
adversarial AI detection, and cloud-native security monitoring. It operates across
three domains:

1. **Local Network Monitoring** — Packet-level analysis on physical machines
2. **Cloud Infrastructure Monitoring** — VPC Flow Log and CloudTrail analysis on AWS/Azure
3. **Web-Layer Protection** — Browser-based threat detection via extension

These three domains feed into a unified backend that classifies, correlates, and
responds to threats through a single real-time dashboard.

### 1.3 System Components

| Component | Codename | Description |
|---|---|---|
| Local Agent | **The Eye** | C++ packet capture + Python ML classification engine |
| Cloud Agent | **The Oracle** | Python-based cloud log ingestion and classification |
| Backend API | **The Citadel** | Java Spring Boot orchestration, response engine, and data store |
| Dashboard | **The Lens** | React TypeScript real-time monitoring interface |
| Browser Extension | **The Ward** | TypeScript web-layer threat detection (standalone + connected) |
| Honeypot Fleet | **The Lure** | Terraform-provisioned decoy servers for attack data collection |

### 1.4 Design Goals

- **Performance:** The Eye must handle sustained traffic analysis at 1 Gbps
  without packet loss
- **Accuracy:** Attack classification must achieve >95% precision and >90% recall
  on known attack categories, with a false positive rate below 2%
- **Autonomy:** Tiered response model — Observe → Recommend → Act — with
  confidence thresholds governing escalation
- **Portability:** The Eye must run on macOS (primary dev), Linux, and
  Windows (stretch goal)
- **Cloud-Native:** The Oracle must ingest and classify AWS VPC Flow Logs,
  CloudTrail events, and Azure NSG Flow Logs
- **Extensibility:** New attack signatures, response playbooks, and data sources
  can be added without modifying core system logic

### 1.5 Non-Goals (Scope Boundaries)

- Providence is NOT an offensive security tool. It does not probe, scan, or
  transmit to external systems.
- Providence is NOT a replacement for enterprise SIEM (Splunk, etc.).
- Providence does NOT attempt real-time decryption of encrypted traffic.
  Encrypted traffic analysis is limited to flow metadata, timing patterns,
  packet size distributions, TLS fingerprinting (JA3/JA3S), and DNS queries.
- Providence does NOT "hack back" or interfere with attacker systems.

## 3. Data Flow

### 3.1 Local Agent (The Eye) Data Flow

```
Network Interface
    │
    ▼
[Packet Capture - C++/libpcap]
    │  Raw packet → ring buffer (lock-free circular buffer)
    ▼
[Feature Extraction - C++]
    │  Extracts per-packet and per-flow features:
    │  ├── Network: src/dst IP, ports, protocol, TTL
    │  ├── Transport: flags, window size, sequence numbers
    │  ├── Flow: packets/sec, bytes/sec, duration, inter-arrival time
    │  ├── Payload: size, entropy (high entropy → possible encryption/exfil)
    │  ├── TLS: JA3 fingerprint, SNI, cipher suites (from handshake)
    │  └── DNS: query domains, query frequency, response sizes
    │
    │  Feature vector serialized via protobuf
    ▼
[Unix Domain Socket]
    │
    ▼
[ML Classification - Python service]
    │  Classifies into attack taxonomy (see Section 5)
    │  Returns: {category, subcategory, confidence, feature_importances}
    ▼
[Event Dispatcher - C++/gRPC]
    │  Sends classified event to The Citadel
    ▼
[The Citadel - Java Spring Boot]
    │  Applies tiered response logic
    │  Stores event in PostgreSQL
    │  Publishes to Redis pub/sub
    ▼
[The Lens + The Ward]
    Real-time visualization + alerts
```

### 3.2 Cloud Agent (The Oracle) Data Flow

```
AWS/Azure Cloud Environment
    │
    ├── VPC Flow Logs (S3 bucket or CloudWatch)
    ├── CloudTrail Events (S3 bucket)
    └── Azure NSG Flow Logs (Storage Account)
    │
    ▼
[Log Ingestion - Python/boto3/azure-sdk]
    │  Polls or subscribes to log sources
    │  Normalizes heterogeneous log formats into unified schema
    ▼
[Feature Extraction - Python]
    │  Extracts flow-level features matching local agent schema:
    │  ├── Source/destination, ports, protocol, bytes, packets
    │  ├── Accept/reject status (security group decisions)
    │  ├── API call patterns (CloudTrail: who, what, when, from where)
    │  └── Temporal patterns (request frequency, time-of-day anomalies)
    ▼
[ML Classification - Python]
    │  Same models as The Eye, adapted for cloud feature schema
    │  Additional cloud-specific categories:
    │  ├── IAM_ESCALATION (privilege escalation attempts)
    │  ├── RESOURCE_ABUSE (cryptomining, unauthorized compute)
    │  └── DATA_EXPOSURE (S3 bucket enumeration, mass download)
    ▼
[REST dispatch to The Citadel]
    │
    ▼
[Same response pipeline as local agent]
    │  Cloud-native responses via AWS/Azure SDKs:
    │  ├── Update Security Group rules
    │  ├── Revoke IAM credentials
    │  ├── Trigger Lambda/Azure Function for automated remediation
    │  └── Send SNS/Event Grid alerts
```

### 3.3 Browser Extension (The Ward) Data Flow

```
User browses the web
    │
    ▼
[Content Script - TypeScript]
    │  Analyzes each page:
    │  ├── URL reputation check (local blocklist + optional API)
    │  ├── TLS certificate validation
    │  ├── Script analysis (detect cryptominers, tracking, injected code)
    │  ├── Phishing indicators (domain similarity, form targets, urgency patterns)
    │  └── Resource loading analysis (suspicious external domains)
    │
    ├──── [STANDALONE MODE]
    │     Local threat scoring and blocking
    │     User sees warning banner or blocked page
    │
    └──── [CONNECTED MODE - Optional]
          Sends telemetry to The Citadel via REST
          Receives enriched threat intel from backend
          (e.g., "this IP was flagged by The Eye 10 min ago")
          Unified view in The Lens dashboard
```

## 4. Technology Decisions & Rationale

### 4.1 Language Allocation

| Component | Language | Rationale |
|---|---|---|
| Packet Capture | C++ | Performance-critical. libpcap is a C library. Zero-copy packet processing requires manual memory management. Demonstrates systems programming on resume. |
| Feature Extraction | C++ | Hot path alongside capture. Feature extraction from raw packet bytes is pointer arithmetic — C++'s home turf. |
| ML Classification | Python | PyTorch/scikit-learn ecosystem. Not the bottleneck — operates on pre-extracted feature vectors. Runs as separate service via Unix domain socket. |
| Event Dispatcher | C++ | gRPC has excellent C++ support. Keeps The Eye as a cohesive C++ binary with Python ML as an adjacent service. |
| Cloud Agent | Python | boto3 (AWS) and azure-sdk are Python-native. No performance-critical path — cloud logs arrive in batches, not at wire speed. |
| Backend API | Java (Spring Boot) | Enterprise-standard framework. Demonstrates Java proficiency. Spring's WebSocket support, dependency injection, and JPA/Hibernate for database access are production patterns. |
| Dashboard | TypeScript (React) | Industry standard. Real-time updates via WebSocket. |
| Browser Extension | TypeScript | Chrome extension APIs are JavaScript-native. TypeScript adds type safety. |
| Infrastructure | Terraform (HCL) | Industry-standard IaC. Provisions honeypots, cloud monitoring infrastructure, and deployment environments. |

### 4.2 Inter-Component Communication

| Path | Protocol | Rationale |
|---|---|---|
| Eye (C++) ↔ ML Service (Python) | Unix Domain Socket | Lowest-latency IPC for co-located processes. No network overhead. Binary protocol with protobuf serialization. |
| Eye → Citadel | gRPC | High-throughput, schema-enforced (protobuf), bidirectional streaming. Thousands of events/sec — HTTP REST would choke. |
| Oracle → Citadel | REST (HTTPS) | Lower frequency than packet-level events. Cloud logs arrive in batches. REST is simpler and sufficient. |
| Citadel → Lens | WebSocket | Real-time push updates for live traffic visualization. |
| Lens → Citadel | REST | CRUD operations: config changes, playbook edits, manual overrides. |
| Ward → Citadel | REST | Lower-frequency telemetry. Extension reports suspicious URLs/scripts. |

### 4.3 ML Model Strategy

**Phase 1 — Classical ML (scikit-learn)**
- Random Forest or Gradient Boosted Trees on CICIDS2017 / CIC-IDS2018
- Fast inference, interpretable feature importances
- Baseline to beat: published benchmarks on these datasets
- Evaluation: per-category precision/recall/F1, confusion matrix, ROC curves

**Phase 2 — Deep Learning (PyTorch)**
- 1D CNN or LSTM on raw flow sequences for temporal pattern detection
- Specifically targets the AI_AGENT detection module (behavioral sequence analysis)
- Trained on honeypot-collected data (real attacks) + synthetic AI-agent data (lab-generated)

**Phase 3 — Online Learning (stretch)**
- Model updates from confirmed classifications (analyst feedback loop via dashboard)
- Drift detection to flag when traffic patterns shift beyond training distribution

### 4.4 Encrypted Traffic Analysis Strategy

Providence operates on what is visible. For encrypted traffic, analysis is limited to:

| Feature Category | Available Despite Encryption | Detection Capability |
|---|---|---|
| Flow metadata | Source/dest IP, ports, protocol, timestamps | DOS, PROBE, BRUTE_FORCE |
| Packet size distributions | Payload lengths per packet | EXFILTRATION (sustained large outbound) |
| Timing patterns | Inter-arrival times, connection duration, frequency | AI_AGENT (automated patterns), BRUTE_FORCE |
| TLS fingerprinting | JA3/JA3S hashes from handshake | Tool identification (Metasploit, curl, Python requests, malware families) |
| DNS queries | Queried domains (unless DoH/DoT) | EXFILTRATION (DNS tunneling), C2 communication |
| Certificate metadata | Cert chain, validity, issuer | Phishing (self-signed certs, recently issued certs) |

**Payload inspection** (for INJECTION detection) is limited to unencrypted HTTP traffic. This limitation is documented and scoped honestly.

## 5. Attack Taxonomy & Response Playbooks

### 5.1 Classification Categories

#### Local Agent (The Eye) Categories

| Category | Subcategories | Example Indicators |
|---|---|---|
| BENIGN | Normal traffic | Matches baseline flow statistics |
| DOS | SYN flood, UDP flood, Slowloris, HTTP flood | High packet rate from single source, incomplete handshakes, slow partial requests |
| PROBE | Port scan, OS fingerprint, vulnerability scan | Sequential port access, TTL manipulation, banner grabbing |
| BRUTE_FORCE | SSH, FTP, HTTP auth, RDP | Repeated failed auth from single source, credential stuffing patterns |
| INJECTION | SQL injection, XSS, command injection | Malicious payloads in HTTP parameters (**unencrypted traffic only**) |
| EXFILTRATION | DNS tunneling, large outbound transfers | Anomalous DNS query patterns, sustained high-volume outbound to unknown hosts |
| AI_AGENT | LLM-driven attack automation | Systematic exploration patterns, semantically coherent but templated requests, adaptive behavior across blocked attempts, characteristic LLM response latencies |

#### Cloud Agent (The Oracle) Additional Categories

| Category | Subcategories | Example Indicators |
|---|---|---|
| IAM_ESCALATION | Privilege escalation, role assumption | Unusual AssumeRole calls, policy attachment to unauthorized users |
| RESOURCE_ABUSE | Cryptomining, unauthorized compute | Unexpected EC2/VM launches, GPU instance creation, high compute in off-hours |
| DATA_EXPOSURE | S3 enumeration, mass download | ListBucket calls across many buckets, large GetObject volumes, public access changes |

### 5.2 Tiered Response Model

```
CONFIDENCE THRESHOLD          ACTION                     REVERSIBLE?
─────────────────────────────────────────────────────────────────────
< 0.60                        OBSERVE                    N/A
                               - Record event to database
                               - Update dashboard feed
                               - No alert generated

0.60 - 0.85                   RECOMMEND                  N/A
                               - Log event with full context
                               - Push alert to dashboard
                               - Generate recommended action
                               - Await human confirmation

> 0.85                         ACT                        YES
                               - Log event with full forensic context
                               - Push critical alert
                               - Execute response playbook:

                               LOCAL RESPONSES:
                                 • Rate limit source IP (pfctl/iptables)
                                 • Add to temporary blocklist
                                 • Tighten firewall rules
                                 • Auto-expire block after TTL

                               CLOUD RESPONSES:
                                 • Update Security Group / NSG rules
                                 • Revoke compromised IAM credentials
                                 • Trigger Lambda remediation function
                                 • Send SNS/Event Grid alert

                               - Generate incident report

ABSOLUTE CONSTRAINTS (ALL CONFIDENCE LEVELS):
─────────────────────────────────────────────────────────────────────
  NEVER probe external systems
  NEVER transmit adversarial payloads
  NEVER modify non-local or non-owned network config
  NEVER take irreversible action without human confirmation
  NEVER access or store packet payload content beyond classification
```

## 7. Honeypot Fleet — Data Collection Strategy

### 7.1 Fleet Architecture

Providence maintains a fleet of honeypot instances across cloud providers and
regions to collect diverse, real-world attack traffic for ML training.

| Honeypot | Provider | Region | Profile | Target Attack Types |
|---|---|---|---|---|
| LURE-SSH | AWS EC2 | us-east-1 | SSH server (cowrie) | BRUTE_FORCE, credential stuffing |
| LURE-WEB | AWS EC2 | eu-west-1 | Web server (dionaea/DVWA) | INJECTION, PROBE, web attacks |
| LURE-DB | AWS EC2 | ap-southeast-1 | Database server | BRUTE_FORCE (DB), DATA_EXPOSURE |
| LURE-IOT | Raspberry Pi | Home network | IoT device (Telnet/UPnP) | Botnet scanning (Mirai variants) |

**Provider consolidation:** All cloud honeypots run on AWS to minimize operational
overhead. Single billing dashboard, single CLI toolchain (aws-cli), single IAM
configuration. AWS free tier covers 750 hours/month of t2.micro for the first
12 months — sufficient for one always-on instance with remaining hours split
across additional instances. After free tier, t2.micro instances cost ~$8.50/month
each. Geographic diversity is achieved via AWS regions rather than provider diversity.

### 7.2 Data Pipeline

```
Honeypot Instances
    │
    ├── LURE-SSH ──► cowrie JSON logs
    ├── LURE-WEB ──► dionaea/access logs
    ├── LURE-DB ──► connection attempt logs
    └── LURE-IOT ──► custom Telnet/UPnP logs
    │
    ▼
[Log Shipping]
    │  Each honeypot ships logs to central S3 bucket
    │  via rsync, CloudWatch agent, or Filebeat
    ▼
[Normalization Pipeline - Python]
    │  Standardizes heterogeneous log formats into
    │  Providence unified event schema:
    │  {timestamp, src_ip, dst_port, protocol,
    │   payload_sample, session_duration, category_label}
    ▼
[Training Data Store - PostgreSQL / Parquet files]
    │
    ▼
[ML Training Pipeline]
```

### 7.3 AI Agent Data Generation (Lab Environment)

For the AI_AGENT classification category, no public dataset exists. Providence
generates its own labeled dataset:

**Setup:**
- Isolated virtual network (2+ VMs on private subnet)
- VM-1: Runs honeypot services (SSH, HTTP, database)
- VM-2: Runs LLM-powered attack automation scripts

**Methodology:**
1. Record real human attack traffic from cloud honeypots (labeled HUMAN)
2. Build simple LLM-driven attack scripts that probe the lab honeypot:
   - Automated SSH credential guessing with adaptive wordlist generation
   - Web vulnerability scanning with LLM-guided payload crafting
   - API fuzzing with semantically-aware parameter exploration
3. Record LLM-generated attack traffic (labeled AI_AGENT)
4. Train sequence model on behavioral differences:
   - Timing patterns (LLM inference latency vs. human reaction time)
   - Exploration strategy (systematic vs. intuitive)
   - Adaptation patterns (how quickly and in what way attempts change after failure)

**Limitations (documented honestly):**
- Synthetic data may not represent all AI attack tools
- Behavioral signatures may change as AI attack tools evolve
- Model is trained on self-generated AI traffic, not independently validated
- This module is explicitly experimental/research-grade

### 7.4 Deployment

Honeypots are provisioned via a Terraform module:

```hcl
# Example: Deploy a new honeypot
module "lure_ssh" {
  source        = "./modules/honeypot"
  ami           = "ami-0c55b159cbfafe1f0"  # Ubuntu 24.04 LTS
  instance_type = "t2.micro"
  region        = "us-east-1"
  profile       = "ssh"
  open_ports    = [22, 2222]
  log_bucket    = "providence-honeypot-data"
  log_prefix    = "lure-ssh/"
  tags = {
    Name        = "LURE-SSH"
    Environment = "honeypot"
    Project     = "Providence"
  }
}
```

One `terraform apply` → new honeypot is live with logging configured and
shipping to a central S3 bucket.

**Cost estimate:** ~$10-25/month depending on free tier eligibility and
number of active instances. Set AWS Budget alerts at $15 and $30 thresholds.

**Timeline:** Deploy LURE-SSH and LURE-WEB in Week 1 of the project. Add remaining
honeypots over Weeks 2-3. Allow minimum 8-12 weeks of data collection before
using data for ML training.

documented here for future reference.

### ADR-001: Agent-ML Inter-Process Communication
**Decision:** Separate Python inference service communicating via Unix domain socket.
**Alternatives considered:**
- (A) Python subprocess via pipes — rejected due to process creation overhead
- (C) Embedded CPython interpreter — rejected due to complexity (GIL management,
  reference counting bugs, deployment coupling) vs. learning value tradeoff
**Rationale:** Option B provides clean separation of concerns, independent testability,
independent restartability, and teaches socket programming and service contract
design — all of which are professionally relevant.

### ADR-002: Primary Development Platform
**Decision:** macOS as primary development target. Linux via Docker. Windows as stretch.
**Rationale:** Developer's primary machines are macOS and Windows. macOS is Unix-based,
so libpcap and socket code is portable to Linux with minimal changes. pfctl (macOS)
is the first FirewallManager implementation. Linux iptables tested in Docker.
Windows WFP is architecturally different and deferred.

### ADR-003: Encrypted Traffic Scope
**Decision:** Flow-level and metadata analysis for encrypted traffic. Payload inspection
limited to unencrypted HTTP. Documented honestly.
**Rationale:** Industry standard approach (Zeek, Suricata operate similarly). Attempting
decryption is out of scope and legally questionable. Flow metadata, timing, packet
sizes, JA3 fingerprints, and DNS provide sufficient signal for most attack categories.

### ADR-004: Browser Extension Architecture
**Decision:** Standalone by default with optional connection to The Citadel.
**Rationale:** Maximizes usability (no backend dependency) while enabling the unified
platform experience. Mirrors real security product freemium architecture.

### ADR-005: Honeypot Data Strategy
**Decision:** Multi-provider, multi-region honeypot fleet with Terraform provisioning.
Deploy early, collect data passively throughout development.
**Rationale:** ML training data is time-gated. The longer honeypots run, the richer
the dataset. Deploying in Phase 0 ensures months of data collection before Phase 6.
Multiple profiles attract diverse attack types matching the classification taxonomy.

### ADR-006: Cloud Integration Approach
**Decision:** Separate Python-based Cloud Agent (The Oracle) ingesting cloud-native logs.
Same ML models, different data source. Cloud-native responses via AWS/Azure SDKs.
**Rationale:** Cloud logs are structured and arrive in batches — no need for C++ performance.
Python with boto3/azure-sdk is the natural fit. Reusing the classification engine
demonstrates the platform's extensibility.

### ADR-007: Flow Tracking Memory Architecture
**Decision:** Two-tier flow tracking system with LRU general cache and priority-scored
threat cache.
**Alternatives considered:**
- Single LRU cache — rejected because high-volume benign traffic evicts flows
  under active threat investigation
- Multi-level cascade (3+ tiers) — rejected as unnecessary complexity for
  expected traffic volumes
**Design:**
- **Tier 1 (General Flow Table):** Fixed capacity (default 100K flows), LRU eviction.
  All new flows start here. Stores flow metadata and aggregated statistics.
- **Tier 2 (Threat Flow Cache):** Smaller capacity (default 10K flows), priority-scored.
  Flows promoted from Tier 1 when ML classification returns non-BENIGN with
  confidence > 0.4. No LRU eviction — entries removed only on explicit close,
  incident resolution, or hard TTL (24h inactivity). If Tier 2 fills, lowest
  priority-score entries are demoted back to Tier 1.
- **Promotion criteria:** ML confidence > 0.4 for any non-BENIGN category
- **Priority score:** `confidence × severity_weight` where severity weights are
  configurable per attack category (e.g., EXFILTRATION = 1.0, PROBE = 0.5)
**Rationale:** Ensures active threat investigations are never lost due to benign
traffic volume. Two tiers balance memory efficiency with threat tracking fidelity.
Configurable thresholds allow tuning for different network environments.

### ADR-008: Model Deployment Strategy
**Decision:** Shadow scoring evaluation period followed by hot swap with fallback.
**Design:**
1. New model deployed alongside current model in ML service
2. Both models score every incoming feature vector
3. Only current model's classifications drive response decisions
4. New model's predictions logged silently for comparison
5. After evaluation period (48 hours or configurable N classifications),
   performance comparison is generated automatically
6. Operator reviews comparison and triggers swap via `/swap` API endpoint
7. Old model retained in memory during cooldown period for instant rollback
8. If false positive rate spikes post-swap, operator triggers `/rollback`
**Implementation:** `model_registry.py` manages versioned model files.
ML service exposes `/models` (list), `/shadow` (enable), `/swap` (activate),
`/rollback` (revert) endpoints.
**Rationale:** Shadow scoring provides empirical evidence before committing to
a new model. Hot swap avoids downtime. Fallback period mitigates risk of
degraded performance. Pattern mirrors production ML deployment at companies
like Netflix and Uber.

### ADR-009: Dashboard Authentication
**Decision:** JWT-based authentication with role-based access control (RBAC).
Two roles: Admin and Viewer.
**Design:**
- **Admin role:** Full access — modify playbooks, change response thresholds,
  block/unblock IPs, deploy models, configure system settings
- **Viewer role:** Read-only — view dashboard, events, incident reports,
  model metrics. Cannot modify any system state.
- Authentication: POST `/auth/login` with credentials → JWT returned
- JWT included in Authorization header for REST, in handshake for WebSocket
- User store: Spring Security in-memory store with credentials from
  environment variables (no full registration system needed)
**Rationale:** Demonstrates understanding of auth patterns (JWT, RBAC) which
is a common interview topic. Two roles enable safe demos without exposing
system controls. Keeps implementation lightweight — this is a security tool,
not a user management platform.

### ADR-010: Ethics Documentation
**Decision:** Comprehensive ETHICS.md covering honeypot data collection, automated
response constraints, data retention, responsible disclosure, and AI attack
research methodology. See Section 13 for full content.
**Rationale:** Demonstrates ethical maturity and awareness of the dual-use nature
of security tools. Differentiator in portfolio — signals that the developer
understands the implications of the technology they build.

### ADR-011: Azure Parity
**Decision:** AWS primary. Azure as documented future work with abstraction layer
in place.
**Alternatives considered:**
- Full AWS + Azure parity — rejected due to doubled cloud engineering work
  with limited resume ROI given developer's existing AWS familiarity
**Rationale:** The Oracle's plugin architecture supports additional providers.
AWS ingestors (VPC Flow Logs, CloudTrail) are fully implemented. Azure NSG
Flow Log ingestor exists as a placeholder in the directory structure.
Documentation explicitly notes Azure as a planned extension. The provider-agnostic
interface demonstrates extensible design without requiring full implementation.

### ADR-012: Honeypot Fleet Provider Consolidation
**Decision:** All cloud honeypots on AWS. Geographic diversity via AWS regions.
**Alternatives considered:**
- Multi-provider fleet (DigitalOcean + AWS + Azure) — rejected due to
  operational overhead of managing three provider accounts, three CLIs,
  three billing systems, and three Terraform provider configurations
**Rationale:** Single provider simplifies operations, billing, IAM, and
Terraform configuration. AWS regions provide sufficient geographic diversity
for attracting varied attack traffic. Consolidation on AWS aligns with
The Oracle's AWS-first cloud integration strategy.

## 13. Ethics & Responsible Use

Providence is a defensive security tool that involves packet capture, attack data
collection, and automated response actions. This section documents the ethical
framework governing its development and use.

### 13.1 Honeypot Data Collection

Providence deploys honeypot servers to collect real-world attack traffic for ML
training and security research.

**What is collected:**
- Connection metadata (source IP, destination port, protocol, timestamp)
- Authentication attempt logs (usernames, passwords used in brute force)
- Attack payloads (exploit code, injection strings, malware samples)
- Session behavior (commands executed, files uploaded, lateral movement)

**What is NOT collected:**
- Traffic from legitimate users (honeypots have no real users or services)
- Personal identifying information beyond IP addresses
- Data from networks not owned by the project maintainer

**Data handling commitments:**
- IP addresses are anonymized (hashed or masked) in any published datasets,
  documentation, or public-facing materials
- Raw honeypot data is stored in private, encrypted S3 buckets with
  restricted IAM access
- No attempt is made to identify, contact, or retaliate against the
  operators of scanning or attack infrastructure
- Data retention: Raw logs retained for 12 months, then archived or deleted.
  Aggregated/anonymized training datasets retained indefinitely.

### 13.2 Automated Response Constraints

Providence takes autonomous defensive actions when threat confidence exceeds
defined thresholds. The following constraints are hard-coded and cannot be
overridden by configuration:

- **All automated actions are reversible.** Blocks expire after a TTL.
  No permanent firewall modifications without human confirmation.
- **All automated actions are logged** with full forensic context: what
  was detected, what confidence score triggered the action, what action
  was taken, and when it will expire.
- **Providence NEVER takes offensive action.** No probing, scanning,
  transmitting to, or interfering with external systems under any
  circumstances.
- **Providence NEVER modifies network configuration it does not own.**
  Local mode operates only on the host machine's firewall. Cloud mode
  operates only within the authenticated AWS account.
- **Irreversible actions always require human confirmation.** The ACT
  tier only performs time-limited, auto-expiring responses. Permanent
  blocks, credential revocations, or infrastructure changes require
  explicit operator approval via The Lens dashboard.

### 13.3 Packet Capture & Privacy

When operating in local mode, The Eye captures network traffic on the host
machine's network interface. This may include traffic from other devices on
the same local network.

**Privacy commitments:**
- Packet payloads are analyzed for threat classification only. Content is
  not stored for benign traffic.
- For classified threat events, payload samples may be stored for forensic
  purposes with a configurable retention period (default 30 days).
- Providence is not a surveillance tool. It does not log, index, or make
  searchable the content of network communications.
- Users deploying Providence on shared networks should inform other network
  users that traffic monitoring is in effect, consistent with applicable laws.

### 13.4 Responsible Disclosure

If Providence's honeypots or monitoring systems identify a compromised machine
being used as an attack source (e.g., a residential IP running botnet software),
the appropriate response is:

1. Log and document the evidence
2. Report to the relevant ISP abuse contact or national CERT
3. Do NOT attempt to interfere with, notify, or access the compromised machine

Providence generates structured incident reports suitable for submission to
FBI IC3 (Internet Crime Complaint Center) or relevant national CERTs.

### 13.5 AI Attack Research

Providence includes an experimental module for detecting AI-driven attacks.
Developing this module involves creating LLM-powered attack scripts for a
controlled lab environment.

**Research constraints:**
- All AI attack scripts run exclusively in isolated lab environments
  (local VMs on private subnets with no internet access)
- AI attack scripts target only honeypot services operated by the
  project maintainer — never real systems or third-party infrastructure
- AI attack scripts are NOT included in the public repository
- The lab methodology, results, and limitations are fully documented
- This research is defensive in nature: the goal is to understand AI
  attack patterns in order to detect them, not to develop attack capabilities

### 13.6 Dual-Use Acknowledgment

Security tools are inherently dual-use. The same knowledge that enables
detection also enables attack. Providence is designed, documented, and
licensed with defensive use as its explicit and sole purpose.

The project maintainer acknowledges this tension and has made deliberate
design choices to limit offensive applicability:
- No offensive capabilities are implemented or planned
- Detection signatures and response playbooks are published; attack
  generation code is not
- The ETHICS.md file and this section exist to make the project's
  defensive intent unambiguous

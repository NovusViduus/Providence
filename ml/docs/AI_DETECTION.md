# Providence — Adversarial AI Agent Detection

> This entire module is explicitly experimental. No public ground truth exists for AI-agent attack traffic.

## Methodology

### HUMAN Data Collection
- Source: The Lure honeypot infrastructure across 3 AWS regions (us-east-1, eu-west-1, ap-southeast-1)
- Collection period: February–April 2026
- **282,863 sessions** (183,933 BRUTE_FORCE, 92,726 PROBE, 6,204 EXFILTRATION)
- Normalized via `scripts/normalize/cowrie_to_providence.py` into unified event schema with per-session timing data

### AI_AGENT Data Generation
- Lab environment: isolated Docker network with Cowrie SSH honeypot + Python attacker container
- LLM: Anthropic Claude (claude-sonnet-4-20250514) for credential generation and command selection
- Attack scripts: `ssh_credential_guesser.py` (credential guessing with LLM-guided adaptation) and `adaptive_explorer.py` (post-auth exploration with context-aware command selection)
- Each session captures real LLM inference latency in inter-attempt timing (typically 1–5 seconds)
- Target: ≥200 AI_AGENT sessions generated

### Behavioral Features (24 features per session)

Timing: inter_attempt_mean/std/min/max/cv/median, attempt_rate, session_duration
Exploration: unique_usernames/passwords, credential_diversity, username/password_entropy, success_ratio
Command sequence: command_count, unique_commands, command_diversity, recon_command_ratio, download_attempt, lateral_movement, command_inter_time_mean/std
Adaptation: strategy_shift_count, retry_after_block

### Models Trained
1. XGBoost tabular baseline — aggregate behavioral features, no sequence modeling
2. 1D CNN — multi-kernel (3,5,7) convolutions over padded event sequences
3. Bidirectional LSTM — 2-layer, hidden_dim=64, over padded event sequences

Binary classification: HUMAN=0, AI_AGENT=1. BCE loss, Adam optimizer, early stopping.

The tabular baseline provides the comparison point: if sequence models don't outperform it, the temporal structure isn't adding value beyond aggregate statistics.

## Limitations

This section is the most important part of this document.

1. **Synthetic AI class.** The AI_AGENT class is defined by a specific LLM (Claude) with specific prompts running specific attack scripts. A different LLM, different prompting strategy, or custom attack tooling would produce different behavioral patterns. The model detects *this kind* of AI automation, not all possible AI automation.

2. **HUMAN class includes bots.** The HUMAN class from honeypot data includes traditional automated bots (Mirai variants, credential stuffers), not just literal humans typing. The real distinction being learned is "traditional automation" vs "LLM-guided automation" — a subtle boundary.

3. **Small dataset.** ~200–500 AI_AGENT sessions is small for deep learning. The CNN and LSTM may overfit. The tabular XGBoost baseline may perform comparably with less overfitting risk. If so, that's a valid finding — it means aggregate timing statistics capture most of the signal.

4. **Lab environment artifacts.** The lab Docker network has different latency, jitter, and load characteristics than real attacks traversing the internet. Network conditions affect timing features, which are the strongest hypothesized signal.

5. **LLM latency is ephemeral.** LLM inference latency (the strongest hypothesized signal) changes as models get faster, as providers add response caching, or as attackers run local models with different latency profiles. A model trained on 2026 Claude latency may not generalize to 2027 inference speeds.

6. **No real-world validation.** The model has not been validated against confirmed real-world AI-driven attacks because no labeled ground truth exists. The lab data is the only source of AI_AGENT labels.

7. **Adversarial evasion is trivial.** An attacker aware of timing-based detection could add random delays between actions to mimic human timing patterns. The model provides no robustness against deliberate evasion.

8. **Single LLM source.** All AI_AGENT data comes from one LLM (Claude). GPT-4, Gemini, Llama, or custom fine-tuned models would produce different behavioral signatures. Multi-LLM training data would improve generalization.

9. **Research contribution, not production system.** This module demonstrates the methodology for behavioral AI detection — hypothesis formation, synthetic data generation, feature engineering, model training, honest evaluation. It is not a solved problem.

## Future Work

- Adversarial robustness testing: can an attacker defeat timing-based detection by adding random delays?
- Multi-LLM training: generate data from GPT, Gemini, and local models to improve generalization
- Real-world validation: deploy in monitoring mode, manually label flagged sessions
- Continual learning: retrain as LLM capabilities and latency profiles evolve
- Feature expansion: SSH client fingerprinting (HASSH), TLS behavior, DNS query patterns
